Build a scalable IoT management system with strict separation between server-side management logic and ESP runtime behavior, including robust offline/online synchronization and admin-only configuration controls.

---

FEATURES:

## 1. Multi-ESP System
- Support multiple ESP devices.
- Each ESP has a unique server-generated ID.
- ESPs are stored and managed in database.

---

## 2. Admin-Only Configuration Page
- Only Admin can access configuration page.
- Admin can:
  - Rename ESP devices
  - Rename relays inside each ESP
  - Assign friendly names to relays (Relay 1 → “Living Room Light”)
- All naming changes are stored in server database only.
- ESP receives updated labels but does not control naming logic.

---

## 3. Relay Management Model
- Each ESP contains multiple relays.
- Each relay has:
  - ID (fixed, hardware-based)
  - Name (server-defined, editable by admin)
  - State (ON/OFF)

---

## 4. Server vs ESP Responsibility Separation
- ESP does NOT know anything about:
  - Admin
  - User roles
  - Permissions

ESP only handles:
- Relay states (ON/OFF)
- Relay IDs
- Sync with server

All role-based logic is strictly server-side.

---

## 5. State Synchronization System
- Database is the source of truth for relay states and metadata.
- ESP maintains local cache of:
  - Last known relay states
  - Last known configuration

Sync behavior:
- ESP periodically syncs with server when online.
- Server updates are pushed to ESP when connected.

---

## 6. Power Loss Recovery
- If ESP loses power and restarts:
  - It reloads last known state from local storage.
  - Then syncs with server when connection is available.
- No data loss for relay states.

---

## 7. Offline Mode (Access Point Mode)
- If internet connection is lost:
  - ESP activates Access Point mode.
  - Uses last cached server state.
  - Continues operating normally offline.
- Offline mode does NOT expose admin/user logic.

---

## 8. Reconnection Sync Flow
When ESP reconnects to internet:
- ESP sends all pending state updates to server.
- Server updates database accordingly.
- Server responds with latest configuration (names, states).
- ESP updates local cache.

Conflict handling:
- Server is the source of truth.
- Last-write-wins strategy applies unless overridden.

---

## 9. Role-Based Access Control (Server Side Only)
- Admin:
  - Full system control
  - Configuration access
  - Device management
- User:
  - Can only view/operate assigned ESPs

ESP is unaware of roles completely.

---

## 10. UI/UX Improvements
- Single action button expands into multiple actions.
- Clean dashboard per ESP.
- Separate admin and user dashboards.
- Simplified navigation structure.

---

CONSTRAINTS:
- Supabase backend required.
- Real-time sync preferred.
- Secure server-side enforcement (RLS required).
- ESP must function independently in offline mode.
- No role logic on ESP firmware.

OUTPUT EXPECTED:
- System architecture design
- Database schema updates
- Sync protocol design
- UI structure for admin/user dashboards
